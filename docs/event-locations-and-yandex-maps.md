# Места проведения и интеграция с Яндекс Картами

> Актуальное решение для MVP: frontend использует OpenStreetMap как подложку и
> передаёт выбранные пользователем координаты. Backend не обращается к API карт,
> а валидирует и хранит координаты собственного мероприятия. Описанные ниже
> варианты Яндекс API оставлены как исследовательская история.

Статус: концепт, решение не реализовано.

Зафиксировано 25.09.2026. Документ описывает предполагаемое взаимодействие
frontend, backend и сервисов Яндекс Карт при выборе и отображении места
проведения мероприятия. До отдельного решения по лицензии изменения в OpenAPI,
схему БД и код не вносить.

## Задача

На карте необходимо различать три вида объектов:

1. Объекты базовой карты Яндекса: улицы, здания, организации и другие POI.
   Они отображаются картографическим слоем Яндекса, не принадлежат Poydem и не
   загружаются из нашего backend.
2. Места проведения мероприятий Poydem. Их координаты должен возвращать наш
   backend вместе с данными мероприятий, а frontend — отображать как маркеры.
3. Результаты поиска при создании или редактировании мероприятия. Они нужны
   только для выбора площадки организатором и не являются собственным каталогом
   мест Poydem.

Цель интеграции — помочь организатору найти или указать место, сохранить место
конкретного мероприятия и затем независимо от повторного поиска показать его на
карте.

## Возможности API Яндекс Карт

### Geosuggest API

Возвращает поисковые подсказки по мере ввода. Поддерживает географические
объекты и организации; фильтр `types=biz` ограничивает выдачу организациями.
Результат может содержать URI объекта, который затем используется для получения
подробной информации.

Документация: [Geosuggest API](https://yandex.ru/maps-api/docs/suggest-api/index.html).

### Organization Search API

Ищет организации и топографические объекты по тексту и области поиска. Для
организаций используется `type=biz`. Ответ может содержать идентификатор,
название, адрес, категории, контакты, часы работы и координаты.

Основной HTTP endpoint:

```http
GET https://search-maps.yandex.ru/v1/
    ?apikey=...
    &text=Лужники
    &type=biz
    &lang=ru_RU
    &ll=37.6176,55.7558
```

Координаты в ответах Яндекса передаются в порядке
`[longitude, latitude]`. Во внутреннем API Poydem лучше использовать явно
именованные поля `latitude` и `longitude`, чтобы избежать перестановки значений.

Документация: [Organization Search API](https://yandex.ru/maps-api/docs/geosearch-api/index.html),
[параметры запроса](https://yandex.ru/maps-api/docs/geosearch-api/request.html),
[формат ответа](https://yandex.ru/maps-api/docs/geosearch-api/response.html).

### Geocoder API

Преобразует адрес в координаты и координаты в адрес. Подходит для произвольного
адреса или точки на карте, но не является полным каталогом организаций.

Документация: [Geocoder API](https://yandex.ru/maps-api/docs/geocoder-api/index.html).

## Почему не нужен предварительный импорт всех мест

Organization Search является поисковым сервисом, а не API полной выгрузки
справочника. Выдача ограничена, ранжируется по релевантности и не гарантирует
перечисление всех организаций в выбранной области. Попытка обходить город
частями не даст надёжного полного набора и потребует постоянной синхронизации
закрытых, переехавших и изменившихся организаций.

Поэтому не принимается ни frontend-парсинг, ни backend-парсинг всего каталога
Яндекса. Backend также не должен считать отсутствие внешнего места в нашей БД
достаточным основанием для автоматического создания доверенной записи.

## Рекомендуемое взаимодействие

Предпочтителен гибридный вариант:

```text
Организатор вводит название или адрес
        ↓
Frontend запрашивает подсказки Geosuggest
        ↓
Организатор выбирает результат
        ↓
Frontend получает сведения и координаты объекта
        ↓
Frontend показывает маркер и просит подтвердить место
        ↓
Frontend отправляет место вместе с мероприятием в backend
        ↓
Backend валидирует и сохраняет место мероприятия
        ↓
Backend отдаёт координаты мероприятий для отображения на карте
```

Распределение ответственности:

- frontend отвечает за карту, интерактивные подсказки, выбор результата и
  предварительное отображение маркера;
- backend остаётся источником данных о мероприятиях, проверяет структуру,
  допустимые диапазоны координат и сохраняет итоговое место;
- Яндекс используется как внешний источник поиска, но не как наша основная БД;
- при чтении каталога frontend получает координаты мероприятий от Poydem и не
  геокодирует каждый адрес повторно;
- при повышенных требованиях к достоверности backend может повторно разрешить
  внешний идентификатор через API, если это допускают выбранный тариф и лицензия.

Для произвольной точки без организации frontend позволяет поставить маркер на
карте, при необходимости выполняет обратное геокодирование и предлагает
организатору подтвердить или отредактировать название и адрес.

## Предполагаемый API-контракт

Сейчас событие содержит `locationName` и `address`. Этого недостаточно для
стабильного отображения маркера: без координат frontend пришлось бы повторно
геокодировать адрес при каждом открытии карты.

После принятия решения контракт можно расширить вложенным объектом:

```json
{
  "location": {
    "name": "Большая спортивная арена «Лужники»",
    "address": "Москва, Лужники, 24",
    "coordinates": {
      "latitude": 55.715765,
      "longitude": 37.553497
    },
    "provider": "yandex",
    "externalId": "..."
  }
}
```

`provider` должен также поддерживать значение `manual` для места, указанного
без выбора организации из внешнего справочника. Внешний идентификатор является
необязательным: организация может отсутствовать, измениться, закрыться или быть
объединена с другой записью.

Если потребуется поиск по расстоянию, координаты целесообразно хранить как
`geography(Point, 4326)` в PostGIS. Для MVP достаточно отдельных числовых полей
широты и долготы при строгой проверке диапазонов.

## Хранение места в БД

Для первой версии отдельный справочник мест не обязателен. Снимок места можно
хранить вместе с мероприятием:

```text
location_name
address
latitude
longitude
location_source
external_place_id nullable
```

Это сохраняет место мероприятия таким, каким его подтвердил организатор, даже
если внешний поставщик позже изменит карточку организации.

Отдельная таблица `places` оправдана, только если появятся:

- страницы площадок;
- повторное использование одной площадки несколькими мероприятиями;
- поиск и фильтрация по площадке;
- централизованное обновление сведений о площадках.

В таком случае внешние записи дедуплицируются по `(provider, external_id)`, а
событие всё равно хранит необходимый снимок места. Возможность хранить сведения
внешнего поставщика сначала должна быть подтверждена лицензией.

## Лицензионное ограничение

Стандартные условия API Яндекс Карт ограничивают постоянное хранение,
переработку и повторное использование данных ответа. В общих условиях описано
только временное кэширование данных, необходимое для работы сервиса, сроком до
30 дней. Постоянное сохранение адресов, организаций и координат, полученных из
API, может потребовать расширенной коммерческой лицензии.

Проксирование запросов через backend скрывает ключ и помогает контролировать
квоты, но не даёт дополнительных прав на хранение данных. Нельзя считать, что
подтверждение результата пользователем автоматически превращает все данные
Яндекса в собственные данные Poydem.

Перед реализацией требуется проверить актуальные условия конкретных продуктов и
тарифа в кабинете разработчика либо получить письменное подтверждение Яндекса.
Если подходящая лицензия недоступна, для собственного постоянного каталога мест
нужно выбрать источник, разрешающий хранение, например OpenStreetMap с
соблюдением ODbL и правил используемого сервиса.

Источники: [условия использования API Яндекс Карт](https://www.yandex.ru/legal/maps_api/ru/),
[тарифы](https://yandex.ru/maps-api/tariffs).

## Отложенные решения

До начала реализации необходимо определить:

1. Разрешает ли выбранная лицензия сохранять координаты, адрес и идентификатор
   выбранного объекта без ограничения срока.
2. Выполняется ли разрешение выбранного объекта только на frontend или backend
   дополнительно проверяет его по внешнему идентификатору.
3. Хранятся ли поля места непосредственно в событии или вводится отдельная
   сущность `places`.
4. Нужен ли PostGIS и поиск мероприятий по расстоянию уже в MVP.
5. Какой поставщик используется для мест, если условия Яндекса не подходят для
   постоянного хранения.

До ответов на эти вопросы текущие `locationName` и `address` остаются без
изменений, а интеграция с картой не реализуется.
