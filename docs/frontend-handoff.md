# Сообщение фронтендеру: уточнения Poydem API v1

Привет! Это исходное сообщение с вопросами к frontend. Все вопросы уже закрыты;
итоговые решения находятся в [ответах фронтенда](frontend-handoff-answers.md) и
имеют приоритет над предложениями ниже. Исходный OpenAPI ещё нужно обновить,
после чего frontend потребуется пересобрать сгенерированные типы и моки.

## Что уже определено

**Авторизация.** В MVP будут Google, Telegram и VK, подключаем в таком порядке.
Email/password нет. Access JWT живёт 15 минут, refresh — 30 дней и передаётся
через HttpOnly + Secure cookie; backend ротирует его. Refresh нельзя читать из JS.
Logout завершает текущую сессию, ban отзывает все сессии и запрещает защищённые
запросы. Ошибка USER_BANNED — повод показать блокировку, а не бесконечно повторять refresh.

**Onboarding и профиль.** После входа для заполненного профиля нужны firstName
и город. До этого `user.city` может быть `null`; необязательные поля не должны
ломать отображение. Пустые коллекции — `[]`. Организатора компании определяем
по `company.owner.id === user.id`, отдельной системной роли организатора нет.

**PATCH.** Отправляем только изменённые поля. Отсутствующий ключ — не менять,
`null` — очистить nullable-поле, значение — заменить. Например, `{ "about": null }`
очищает описание. Для коллекции интересов пустой `interestIds: []` означает
замену на пустой список; `null` для массива нельзя считать эквивалентом `[]`
без явного nullable в итоговой схеме. Обязательные поля нельзя очищать через null.

**Списки.** Все растущие списки переходят на одну обёртку:

```json
{
  "items": [],
  "pagination": { "page": 1, "limit": 20, "total": 0, "totalPages": 0 }
}
```

Для пустого списка `totalPages: 0` подтверждён.
Подтверждённые значения: page=1, limit=20, максимум limit=100. Обёртка потребуется
для моих событий/компаний/заявок, участников события, компаний события, членов и
заявок компании, административных списков. Сейчас многие из них в OpenAPI описаны
простым массивом. Предлагаю оставить справочники cities/interests/event-categories
массивами — подтвердим точный перечень при обновлении схемы.

**События.** Новое событие ожидает модерации. Автор видит свои ожидающие и
отклонённые события. Публичный каталог по умолчанию показывает активные будущие
события, сортировка — startsAt ASC, id ASC; popular — participantsCount DESC, id ASC.
Backend завершает событие после endsAt, а если его нет — после startsAt.
Все даты передаём в ISO 8601 с часовым поясом, отображаем в выбранном часовом поясе UI.
«Мои события» объединяют созданные и посещаемые события без дубликатов.

**Компании и участие.** Владелец входит в лимит мест: maxMembers=6 означает
владельца и максимум 5 остальных. Владелец не может выйти, передачи владения нет;
ему доступно удаление компании. Один пользователь может быть только в одной
компании одного события. Вход из solo в компанию переключает участие без отдельного
подтверждения. Выход или исключение отменяют участие полностью — solo не сохраняется.
После таких действий нужно обновить состояние участия, списки и счётчики события.

Close закрывает набор и сохраняет участников; open может открыть набор снова,
если событие актуально и компания не заблокирована. Удаление компании скрывает её,
отменяет pending-заявки и участие её пользователей. Административный block скрывает
компанию и запрещает вступление, но сохраняет существующих участников и историю.
Для удаления и выхода нужны разные пояснения в интерфейсе.

**Заявки.** Одна pending-заявка на пользователя и компанию. После rejected/cancelled
можно подать снова, создаётся новая запись. `/applications/me` возвращает pending,
а при её отсутствии — последнюю заявку: наличие ответа 200 само по себе не означает
активную заявку, нужно смотреть её status. Заявка не резервирует место: даже при
отображавшемся свободном месте approve/join может вернуть конфликт. При 409 нужно
показать бизнес-ошибку и обновить данные, а не считать действие выполненным.

**Аватары.** Multipart-поле `file`, JPEG/PNG/WEBP, максимум 5 242 880 bytes. Успешный ответ:
`{ "avatarUrl": "https://..." }`. При ошибке загрузки предыдущий аватар сохраняется.

**Ошибки.** Общая форма `{ error: { code, message, details } }`. Ветвление UI делаем
по code, а не по тексту message. Основные HTTP-коды: 400 — валидация, 401 — проблемы
авторизации, 403 — запрет, 404 — объект отсутствует/недоступен, 409 — конфликт состояния.
Конкретный mapping бизнес-кодов ещё внесём в OpenAPI. В диагностике сохраняйте
`X-Request-ID` ответа: он связывает ошибку с backend-логами.
