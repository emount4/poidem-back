# Handoff фронтенду: подключение к актуальному Poydem API

Статус на 26.09.2026. Документ составлен после сверки актуального backend и
текущего frontend в `poidem-front/Poidem`. Он перечисляет именно необходимые
изменения UI и API-клиента; схемы запросов здесь намеренно не дублируются.

## Что передать фронтендеру

Минимальный комплект:

1. Этот документ — текущий список работ.
2. [`api/openapi.yaml`](../api/openapi.yaml) — единственный источник endpoint-ов,
   DTO, nullable-полей, `operationId` и кодов ошибок.
3. [`frontend-contract.md`](frontend-contract.md) — правила авторизации, refresh,
   PATCH, ошибок и пагинации.
4. [`event-locations-and-yandex-maps.md`](event-locations-and-yandex-maps.md) —
   согласованная ответственность карты и backend. Для MVP используется OpenStreetMap.

Дополнительно, если нужны продуктовые правила компаний, заявок, блокировок и
модерации: [`backend-requirements-poydem.md`](backend-requirements-poydem.md).

Необязательно передавать ERD и план backend-разработки: frontend не должен
зависеть от таблиц БД. `frontend-handoff.md` и `frontend-handoff-answers.md`
содержат историю обсуждения и местами описывают более старое состояние; при
расхождении всегда использовать OpenAPI и этот документ.

## Что уже можно использовать

Локальный API работает на `http://localhost:8080`, prefix — `/api/v1`.
Во frontend для текущей Vite-конфигурации достаточно:

```dotenv
VITE_API_MODE=backend
VITE_BACKEND_URL=http://localhost:8080
```

Backend уже поддерживает регистрацию и вход по логину/паролю, refresh-cookie,
профиль и аватар, каталог и карту событий, создание и модерацию событий,
компании и заявки, жалобы и административные операции.

## P0 — исправить перед дальнейшей разработкой

### 1. Использовать настоящий справочник интересов

`api.dictionaries()` уже возвращает `{ cities, interests, categories }`, но
`App.tsx` сохраняет только города и категории, а в `Onboarding` и
`UserDashboard` передаёт `categories` как интересы. В результате frontend
отправляет идентификаторы категорий мероприятий в `interestIds`.

Нужно:

- добавить отдельный state `interests`;
- заполнять его из `dicts.interests`;
- передавать его в onboarding и редактор профиля;
- не хранить ID справочников в коде и не предполагать, что ID одинаковы между БД.

Backend сейчас возвращает 24 интереса, включая `psychology`, `science`, `walks`
и `yoga-and-health`.

### 2. Синхронизировать TypeScript-типы с OpenAPI

В ответах backend ключи присутствуют всегда, но могут содержать `null`:

```ts
type User = {
  gender: "male" | "female" | "other" | null;
  birthDate: string | null; // YYYY-MM-DD
};

type Company = {
  minAge: number | null;
  maxAge: number | null;
};
```

Поэтому эти поля в response-моделях не должны быть optional через `?`. Для
PATCH-моделей optional означает «поле не отправлено», а `null` — «очистить».
Лучше генерировать типы и API-клиент из OpenAPI, а не поддерживать response DTO
вручную.

### 3. Исправить обычный и административный вход

Форма входа по логину/паролю должна быть обычной пользовательской формой.
После `POST /auth/login`:

- сохранить access token только в памяти;
- показать обычный интерфейс для `role=user`;
- открыть admin-интерфейс только при `role=admin`.

Текущий `backendApi.loginAdmin(username, password)` игнорирует оба аргумента и
пытается вызвать `getCurrentUser()`. Нужно выполнять реальный password login и
затем проверять `user.role`. Не показывать в production подсказку с захардкоженным
паролем администратора.

### 4. Не подставлять фиктивные координаты на карте

Маркеры Poydem должны строиться только из `event.location`, полученного от
backend. Текущий fallback по `cityId` может поставить событие в другом городе:
идентификаторы городов не являются координатами и не фиксированы между базами.

Правило отображения:

- есть `location` — показать маркер `[latitude, longitude]`;
- `location === null` — оставить событие в списке, но не рисовать неточный маркер;
- при движении карты можно запрашивать `/events` с `west/south/east/north`;
- frontend не должен повторно геокодировать каждое событие при чтении.

### 5. Обрабатывать ошибки по `error.code`

Текст `error.message` можно показывать пользователю, но ветвление UI выполнять
по `error.code`:

- `VALIDATION_ERROR` — разложить `error.details.fields` по полям формы;
- `USERNAME_TAKEN` — ошибка поля логина регистрации;
- `INVALID_CREDENTIALS` — ошибка формы входа;
- `PROFILE_INCOMPLETE` — направить в onboarding;
- `AGE_RESTRICTION` — показать ограничение компании; если у текущего пользователя
  `birthDate === null`, предложить заполнить профиль;
- `COMPANY_FULL`, `APPLICATION_ALREADY_EXISTS`, `ALREADY_IN_EVENT_COMPANY` —
  показать бизнес-ошибку и обновить компанию/заявку;
- `USER_BANNED` — завершить пользовательский сценарий без refresh-loop.

Сохранять `X-Request-ID` рядом с диагностикой ошибки.

## P1 — пользовательский MVP

### Профиль и onboarding

- Пол (`gender`) и дата рождения (`birthDate`) поддержаны в GET/PATCH профиля.
- `birthDate` имеет формат `YYYY-MM-DD`; в date picker запретить будущие даты.
- По backend-контракту эти поля nullable. Полнота onboarding определяется только
  непустым `firstName` и выбранным `city`, то есть frontend не должен вычислять
  `isProfileComplete` самостоятельно.
- Если продукт оставляет дату рождения необязательной, перед вступлением в
  возрастную компанию нужно объяснять, зачем её заполнить.
- Добавить удаление аватара через `DELETE /users/me/avatar`.
- Имена/аватары владельцев и участников сделать ссылками на
  `GET /users/{userId}` и экран публичного профиля.

### Создание мероприятия

На лендинге после входа нужна кнопка «Создать мероприятие» и форма:

1. Загрузить обложку через `POST /uploads/events` (`file`, JPEG/PNG/WebP,
   максимум 10 MiB).
2. Полученный `url` передать как `imageUrl` в `POST /events`.
3. Передать `title`, `categoryId`, `cityId`, `startsAt`, опциональный `endsAt`,
   `description`, `locationName`, `address` и `location`.
4. Для MVP выбор места — точка OpenStreetMap или ручной ввод координат. Отправлять
   `{ latitude, longitude, source: "manual" }`.
5. После `201` показать, что событие создано со статусом `pending` и ожидает
   модерации, а не добавлять его в публичный active-каталог.

В личном кабинете автору также нужны редактирование и удаление своего события:
`PATCH /events/{eventId}` и `DELETE /events/{eventId}`. Редактирование active
события возвращает его на модерацию.

### Карточка мероприятия и участие

- Показывать адрес, время окончания, организатора, число участников и компаний.
- Добавить просмотр участников через `GET /events/{eventId}/participants`.
- Для solo-участия поддержать как вступление, так и отмену.
- После join/leave/create/delete обновлять событие и связанные списки, а не
  изменять только локальный счётчик.
- Добавить создание жалобы на событие, компанию или пользователя через
  `POST /reports`.

### Компании и возраст

Форма создания уже содержит `minAge/maxAge`; дополнительно нужно:

- валидировать каждую границу как 14–100 и `minAge <= maxAge`;
- отображать возрастной диапазон в карточке компании;
- nullable-границу подписывать как отсутствие ограничения;
- при `AGE_RESTRICTION` не считать join/application успешным;
- учитывать, что возраст повторно проверяется backend при approve.

Для владельца компании добавить управление по готовым ручкам: редактирование,
close/open, удаление, список участников и исключение участника. Для участника —
выход из компании. Для заявки пользователя — получение текущей заявки и отмена.

## P1 — административный MVP

Текущая панель уже умеет показывать основные списки, но её нужно довести до
контракта:

- использовать серверную пагинацию и фильтры вместо загрузки `limit=100`;
- получать детали пользователя, события и жалобы отдельными GET;
- при reject/block события запрашивать и отправлять причину;
- добавить удаление события администратором;
- не хранить статические массивы городов и категорий в `AdminPanel` — брать
  справочники с backend;
- после ban/unban/block/moderation инвалидировать соответствующие списки и детали.

## P2 — устойчивость интерфейса

- Хранить в URL фильтры каталога, выбранную страницу и режим списка/карты.
- Использовать реальную `pagination`, а не всегда запрашивать `page=1&limit=100`.
- Для мутаций блокировать повторное нажатие и повторно загружать серверное состояние.
- Разделить состояния initial loading, background refresh, empty и error.
- При старте приложения один раз пробовать refresh-cookie, затем загружать `/auth/me`.
- При параллельных `401` оставлять один общий refresh request и повторять исходные
  запросы не более одного раза.

## Критерии приёмки интеграции

- Onboarding отправляет ID из `/interests`, а не из `/event-categories`.
- Перезагрузка страницы восстанавливает сессию через HttpOnly refresh-cookie.
- Регистрация, обычный вход и admin-вход работают одним credential API.
- Профиль сохраняет/очищает nullable-поля с правильной PATCH-семантикой.
- На карте нет маркеров с придуманными координатами.
- Событие проходит путь: создание → pending → admin approve → публичный каталог.
- Компания отображает возраст, а `AGE_RESTRICTION` корректно обработан для join,
  application и approve.
- Все формы показывают field errors из `details.fields` и сохраняют Request ID.
