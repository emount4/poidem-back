# План разработки Poydem API v1

Обновлено 23.09.2026 по [уточнениям требований](backend-requirements-poydem.md).
Основа: исходный `poydem-openapi.yaml`, уточнения, начальная миграция и текущий код.
Уточнения приняты как требования к реализации; исходный OpenAPI ещё нужно
синхронизировать с ними. Этот план не означает, что перечисленные функции уже реализованы.

## Текущее состояние и объём

Готовы: Gin, `/api/v1`, Request ID, JSON-логи, PostgreSQL, Docker Compose,
начальные миграции, `/health`, `/ready` и базовые тесты. Первый бизнес-модуль —
публичное чтение cities/interests/event-categories — реализован через PostgreSQL,
сервис `catalog` и HTTP. Начальные значения справочников ещё не определены, поэтому база
может корректно возвращать пустые массивы.

В исходном OpenAPI 53 операции: авторизация — 5, профиль — 7, справочники — 3,
события — 8, компании с заявками — 15, создание жалобы — 1, администрирование — 14.
После обновления контракта проверяем полноту по его окончательной версии.

Разрабатываем законченными бизнес-модулями. Внутри модуля рядом находятся модели,
сервисы и интерфейсы, PostgreSQL- и HTTP-адаптеры. DTO принадлежат версии API,
бизнес-правила переиспользуются. Сборка зависимостей остаётся в `internal/app`,
общая инфраструктура — в `internal/platform`. Подробности описаны в
[архитектуре](architecture.md), информация для фронтендера — в
[отдельном сообщении](frontend-handoff.md).

## Принятые решения

В этой таблице названия состояний используются как продуктовые обозначения.
Регистр строковых значений в JSON нужно отдельно согласовать: уточнения используют
верхний регистр, а исходные OpenAPI и SQL — нижний. Это не решение менять значения в API.

| Блок | Зафиксированные требования |
| --- | --- |
| Вход | Google → Telegram → VK, все три в MVP. Первый вход создаёт пользователя; email/password не нужны. Незаполненный профиль ведёт в onboarding. |
| Сессии | Access JWT 15 минут; refresh 30 дней, HttpOnly + Secure cookie; в БД только хеш refresh; ротация; logout отзывает текущую сессию, ban — все сессии. |
| Роли | USER и ADMIN; организатор определяется по `company.owner_id`, отдельной глобальной роли нет. Первый admin создаётся служебно через seed/config/БД. |
| Профиль | Для заполненного профиля нужны firstName и cityId. До onboarding city может быть null. Остальные поля необязательные; пустые коллекции — `[]`. |
| PATCH | Все PATCH частичные: отсутствие поля не меняет значение, null очищает nullable-поле, значение заменяет. Отдельные DTO для создания и обновления. |
| События | Создаёт авторизованный пользователь; начальный статус PENDING. Переходы: PENDING → ACTIVE/REJECTED, ACTIVE → BLOCKED/COMPLETED. Автор видит свои PENDING и REJECTED. |
| Завершение | Система завершает ACTIVE после `endsAt < now`, при отсутствии endsAt — после `startsAt < now`. REJECTED и BLOCKED не видны публично. |
| Каталог | По умолчанию ACTIVE и будущие события; сортировка startsAt ASC, id ASC. Popular: participantsCount DESC, id ASC. Даты ISO 8601, PostgreSQL TIMESTAMPTZ, работа с временем в UTC. |
| Мои события | Объединение созданных событий и событий участия без дублей; фильтры upcoming/past. Поле relation предложено в требованиях, но ещё не описано в OpenAPI. |
| Компания | Создание только для доступного события; owner сразу член компании и участник события, входит в maxMembers. Лимит 2–100 из исходного API. |
| Владелец | Не может выйти через members/me; передачи владения нет. Для прекращения компании использует удаление. |
| Участие | Не более одной компании одного события для пользователя. Solo → company автоматически и атомарно. Выход и исключение отменяют участие целиком, без перехода обратно в solo. |
| Открытый вход | Join без заявки только при joinType=open, доступном событии, открытом наборе, наличии места и допустимом статусе пользователя. |
| Заявки | JoinType=request; одна PENDING на пользователя и компанию. После REJECTED/CANCELLED разрешена новая запись. `/applications/me`: сначала PENDING, иначе последняя. |
| Approve | Повторная проверка места, актуальности компании/события и отсутствия другой компании этого события. Заявка, членство и участие изменяются одной транзакцией. |
| Close/open | Close сохраняет компанию и участников, запрещает новые join/application. Open доступен владельцу, если компания не заблокирована и событие актуально. |
| Удаление | Soft delete через deleted_at. Компания исчезает публично, PENDING заявки отменяются, участие пользователей этой компании удаляется; история членства может сохраняться. Восстановления нет. |
| Ban | Статус banned и отзыв всех refresh-сессий; защищённые endpoints недоступны, история сохраняется. Unban выполняет admin. |
| Block компании | Компания скрыта публично, новые join/application запрещены. Существующие участники и история сохраняются. Это отличается от soft delete. |
| Жалобы | На пользователя, событие или компанию с проверкой существования. Повторные жалобы на объект разрешены. Статусы PENDING/RESOLVED/REJECTED. |
| Аватар | JPEG/PNG/WEBP, максимум 5 MB, проверка фактического типа. Ответ `{ "avatarUrl": "https://..." }`. Старый файл удаляется после успешного сохранения нового. |
| Списки | Все растущие списки: `{ items: [], pagination: { page, limit, total, totalPages } }`. Page=1, limit=20, максимум 100. |
| Ошибки | `{ error: { code, message, details } }`; HTTP 400/401/403/404/409. Коды берём из §25 уточнений, полный mapping фиксируем в OpenAPI. |

## Оставшиеся вопросы и предложения

Эти пункты не отменяют принятые решения. Закрываем их до реализации зависимого блока;
общая HTTP-обвязка и справочники могут разрабатываться независимо.

| Вопрос | Предложение или необходимое уточнение |
| --- | --- |
| Регистр enum | Предлагается сохранить `user/admin`, `pending/active/...`, `solo/company` и `user/event/company` в JSON и БД; error.code — UPPER_SNAKE_CASE. Согласовать с фронтендом до генерации типов. |
| Callback и первый JWT | В контракте callback возвращает 302, механизм выдачи первого access не определён. Предложение: backend ставит refresh-cookie, редиректит на фиксированный frontend callback, frontend получает access через POST refresh. Не передавать токены в URL. Нужны адреса callback и формат ошибки входа. |
| Cookie и браузер | Нужны домены/порты dev и prod, SameSite, Path, CORS и механизм CSRF-защиты. Подтверждённый Secure требует согласованного режима локальной разработки; нельзя молча отключать его в production. |
| Ротация и logout | Определить абсолютные или скользящие 30 дней, обработку повторного refresh и гонок вкладок. Logout завершает текущую сессию; требуется уточнить немедленный отзыв её access JWT или действие до 15 минут. Ban запрещает защищённые запросы сразу, даже с ещё действующим JWT. |
| Onboarding | Уточнить, запрещены ли создание событий, компаний и участие до заполнения профиля. Решить, можно ли очистить city после onboarding; как зарегистрировать пользователя, если провайдер не вернул firstName. Не вводить блокировку молча. |
| Время | Что считать upcoming/past для уже начавшегося события с будущим endsAt; входит ли оно в каталог и доступно ли вступление. Зафиксировать границы dateFrom/dateTo (параметры date), часовой пояс их трактовки и сортировку newest. |
| Ответы «моих» списков | Утвердить relation (`creator`, `participant`, `creator_and_participant`) в отдельном DTO MyEvent; какие исторические, заблокированные и удалённые сущности показываются в моих компаниях/заявках. |
| Пагинация | Явно перечислить списки с новой обёрткой; предложение — справочники остаются массивами. Согласовать totalPages для пустого списка и выход за последнюю страницу. |
| Состояния компаний и заявок | Предложение — набор отражается существующим status active/closed без нового флага. Уточнить approve уже поданной заявки после close, судьбу PENDING при block/completed и повторную подачу после APPROVED с последующим выходом. |
| Скрытые сущности | Уточнить доступ владельца к blocked/deleted компании и автора к blocked событию, видимость сохранённых участников заблокированной компании и их вклад в счётчики. |
| Повторные действия | Для повторного join, solo, leave, close/open, delete и approve/reject утвердить идемпотентный успех или конкретный 409; не пытаться определить это только по HTTP-методу. |
| Ошибки и аватар | Согласовать mapping каждого бизнес-кода в HTTP; недостающие коды запрета выхода owner и членства в другой компании; ответ на файл >5 MB/неподдерживаемый тип и точный лимит в байтах. |
| Статистика | Уточнить период newRegistrations, учёт скрытых записей в dashboard; выбрать служебный способ назначения первого admin. |

## Этап 2. Авторизация и профиль

Зависимость: этап 1 и решения о callback/cookie.

- [ ] Интерфейс провайдера; Google первым. Транзакционное создание users/auth_accounts;
      повторный и одновременный callback не создаёт дубликаты.
- [ ] Новая миграция sessions: user_id, token_hash, expires_at, revoked_at, created_at;
      технические поля для ротации добавить по выбранной реализации.
- [ ] Access JWT 15 минут, refresh 30 дней, HttpOnly+Secure, хеши в БД, атомарная ротация.
      Provider tokens не подменяют собственные access/refresh приложения.
- [ ] Logout текущей сессии, ban всех сессий; проверка актуального banned на каждом
      защищённом запросе, чтобы действующий JWT не обходил бан.
- [ ] GET auth/me и users/me на общем сервисе модуля account, частичный PATCH профиля и интересов
      одной транзакцией. City=null до onboarding, коллекции возвращаются массивами.
- [ ] Настройки callback, cookie/CORS/CSRF и создание первого admin служебным способом.

Готовность: вход, onboarding, обновление сессии и выход работают сквозным сценарием;
проверены истечение, повторный refresh, разные устройства, ban и unban. Реальный
провайдер проверяется после получения client credentials; CI использует тестовый адаптер.

## Этап 3. События, каталог и минимальная модерация

Зависимость: этапы 1–2; чтение можно готовить на фикстурах после этапа 1.

- [ ] POST events создаёт PENDING; валидация справочников, обязательных полей и дат.
- [ ] Каталог ACTIVE/будущих; search/city/category/dateFrom/dateTo, пагинация,
      default startsAt ASC,id ASC; popular participantsCount DESC,id ASC; newest по согласованию.
- [ ] Детали и участники; автору разрешены свои PENDING/REJECTED, публично скрыты
      недоступные состояния. Применять те же правила к вложенным ресурсам.
- [ ] Admin list/details/PATCH и разрешённые approve/reject/block.
- [ ] Идемпотентная фоновая обработка ACTIVE → COMPLETED по endsAt или startsAt;
      при проверке доступности учитывать время независимо от задержки фоновой задачи.
- [ ] participantsCount читать из event_participants; companiesCount учитывать
      согласованную видимость и soft delete. Исключить N+1 и размножение счётчиков JOIN-ами.
- [ ] GET users/me/events: объединение создания/участия без дублей, upcoming/past,
      пагинация и relation после внесения в контракт.

Готовность: создание → модерация → каталог; скрытые состояния не открываются
по прямой ссылке; завершение и границы времени проверены тестами с управляемыми часами.

## Этап 4. Компании и участие

Зависимость: этап 3 и миграции deleted_at/ограничений участия.

- [ ] Создание компании + owner в company_members + участие одним коммитом.
      Owner учитывается в maxMembers и не может выйти; передачи ownership нет.
- [ ] Список компаний события, детали, partial PATCH, участники и мои компании
      с новой пагинацией и фильтрацией исторического членства удалённых компаний.
- [ ] Solo, отмена solo и открытый join; solo → company заменяет одну запись участия.
- [ ] Перед вступлением: пользователь не banned, событие/компания доступны,
      набор открыт, есть место, нет членства в другой компании этого события.
- [ ] Выход и исключение: удалить членство и участие одной транзакцией; обратного solo нет.
- [ ] Close/open: сохранение участников, запрет новых join/application при close;
      ограничения повторного открытия для blocked/deleted/неактуального события.
- [ ] Soft delete: deleted_at, отмена PENDING заявок, удаление только участия,
      привязанного к удаляемой компании; история может сохраняться. Всё атомарно.
- [ ] maxMembers 2–100, уменьшение ниже текущего состава запрещено.
- [ ] Join/create/approve должны использовать общий порядок блокировок и защищать
      и последнее место, и одну компанию на событие. Один count перед insert недостаточен.

Готовность: владелец входит в лимит, не может выйти; solo → company сохраняет
одного участника; leave/kick/delete убирают участие. После soft delete исторические
строки не препятствуют вступлению в другую компанию события. Проверены гонки и откат ошибок.

## Этап 5. Заявки

Зависимость: этап 4; approve использует общий механизм вступления.

- [ ] Создание только для request-компании с открытым набором; одна PENDING
      на company/user защищена частичным UNIQUE в БД.
- [ ] Повторная подача после REJECTED/CANCELLED создаёт новую запись.
- [ ] `/applications/me`: PENDING при наличии, иначе последняя по детерминированному
      порядку created_at DESC,id DESC. Отмена и список моих заявок с согласованной
      видимостью истории и пагинацией.
- [ ] Список заявок владельцу, фильтр статуса; проверять принадлежность applicationId
      companyId из URL и права на approve/reject.
- [ ] Approve атомарно меняет статус/членство/участие после повторной проверки места,
      состояния пользователя, компании, события и отсутствия другой компании события.
- [ ] Заполнять resolved_at; недопустимые повторные переходы дают согласованную ошибку.

Готовность: повторная подача сохраняет историю; параллельные approve/join не
переполняют компанию, approve/cancel не создают отменённую заявку с новым членством.

Готовность: административные операции недоступны обычному пользователю;
ban/block/delete имеют разные, протестированные последствия.

## Изменения БД

Начальную 000001 не переписывать. Добавлять последующие миграции по этапам:

1. Sessions с хешем refresh, сроком и отзывом; ограничения/индексы для безопасной
   ротации и отзыва по user_id. Роли user/admin и статус active/banned после согласования регистра.
2. Companies.deleted_at; max_members 2–100; обязательные поля и начальные состояния
   по правилам API. Перед NOT NULL/CHECK проверить и заполнить существующие данные.
3. Partial UNIQUE applications(company_id,user_id) WHERE status='pending'.
4. Проверка согласованности participation_type/company_id; составной FK компании
   и события либо эквивалентная защита. PK event_participants(event_id,user_id) уже есть:
   дублирующий UNIQUE добавлять не нужно. PK ограничивает запись участия, но сам по
   себе не запрещает противоречивые company_members — нужна общая транзакционная защита.
5. Soft delete не должен превращать исторические company_members в активное членство.
   Не добавлять безусловное ограничение на историю, которое запретит повторное вступление.
6. Индексы для my-lists, пагинации, сессий и фонового завершения выбирать по запросам;
   временные поля заполнять последовательно, не оставлять новые записи без created_at.

## Этап 8. Проверка MVP

- [ ] Контрактные тесты всех операций, nullable/required, PATCH, пагинации и ErrorResponse.
- [ ] Сквозной путь: OAuth → onboarding → создание/модерация события → компания →
      заявка → approve → участие → выход/исключение → жалоба → обработка администратором.
- [ ] JWT/refresh TTL, ротация, logout одного устройства, ban всех устройств;
      запрос с ещё действующим access после ban запрещён.
- [ ] Гонки: последнее место, две компании одного события, create компании при solo/
      другом членстве, approve/cancel, join/delete, join/close и повторный refresh.
- [ ] Owner входит в лимит и не может выйти; участник после leave/kick/delete не
      становится solo; block сохраняет участие; историческое членство не блокирует новый join.
- [ ] Автозавершение с/без endsAt, ongoing, границы UTC и фильтров; стабильная пагинация.
- [ ] Миграции вверх/вниз/повторно на тестовой БД и обновление существующей схемы.
- [ ] Docker с нуля, сохранение данных и файлов, корректное завершение, проверки CI.
