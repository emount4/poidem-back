# План разработки Poydem API v1

Обновлено 23.09.2026 по [уточнениям требований](backend-requirements-poydem.md).
Основа: [`api/openapi.yaml`](../api/openapi.yaml), уточнения, начальная миграция и
текущий код. Согласованные изменения DTO внесены в контракт; отдельные operationId,
полный mapping ошибок и описания прав ещё дополняются по мере реализации.

## Текущее состояние и объём

Готовы: Gin, `/api/v1`, Request ID, JSON-логи, PostgreSQL, Docker Compose,
начальные миграции, `/health`, `/ready` и базовые тесты. Первый бизнес-модуль —
публичное чтение cities/interests/event-categories — реализован через PostgreSQL,
сервис `catalog` и HTTP. Начальные значения справочников ещё не определены, поэтому база
может корректно возвращать пустые массивы.

В исходном OpenAPI 53 операции: авторизация — 5, профиль — 7, справочники — 3,
события — 8, компании с заявками — 15, создание жалобы — 1, администрирование — 14.
После обновления контракта проверяем полноту по его окончательной версии.

Разрабатываем законченными бизнес-модулями. Внутри модуля рядом находятся модели,
сервисы и интерфейсы, PostgreSQL- и HTTP-адаптеры. DTO принадлежат версии API,
бизнес-правила переиспользуются. Сборка зависимостей остаётся в `internal/app`,
общая инфраструктура — в `internal/platform`. Подробности описаны в
[архитектуре](architecture.md). Исходные вопросы и согласованные ответы фронтенда
сохранены в [переписке](frontend-handoff.md) и [решениях](frontend-handoff-answers.md).

## Принятые решения

Все строковые enum в JSON передаются в нижнем регистре. `error.code` использует
`UPPER_SNAKE_CASE`.

| Блок | Зафиксированные требования |
| --- | --- |
| Вход | Google → Telegram → VK, все три в MVP. Первый вход создаёт пользователя; email/password не нужны. Незаполненный профиль ведёт в onboarding. |
| Сессии | Access JWT 15 минут; refresh 30 дней в HttpOnly cookie; ротация с защитой от повторного запроса. Logout отзывает текущую refresh-сессию, ban — все сессии. Access после logout удаляет frontend; после ban backend проверяет статус пользователя на каждом защищённом запросе. |
| OAuth | Callback устанавливает refresh-cookie и делает 302 на `${FRONTEND_URL}/auth/callback`; ошибка ведёт на `/auth/error`. Frontend затем вызывает refresh с `credentials: include`. Токены через URL не передаются. |
| Роли | `user` и `admin`; организатор определяется по `company.owner_id`, отдельной глобальной роли нет. Первый admin создаётся служебно через seed/config/БД. |
| Профиль | `isProfileComplete = firstName != empty && city_id != null`; backend возвращает явный флаг. До завершения разрешено чтение и редактирование профиля/каталога, но создание контента, участие и жалобы возвращают `403 PROFILE_INCOMPLETE`. После onboarding город нельзя очистить. |
| PATCH | Все PATCH частичные: отсутствие поля не меняет значение, null очищает nullable-поле, значение заменяет. Отдельные DTO для создания и обновления. |
| События | Создаёт пользователь с заполненным профилем; начальный статус `pending`. Переходы: `pending → active/rejected`, `active → blocked/completed`. Автор видит свои pending/rejected. |
| Время | При `startsAt <= now < endsAt` событие ongoing: остаётся в каталоге, допускает участие и считается upcoming в личном списке. Completed наступает при `endsAt <= now`, а без endsAt — при `startsAt <= now`. Фильтры предпочтительно передают ISO 8601 date-time с offset; при `format: date` используется UTC. |
| Каталог | Active и ещё не завершённые события; сортировка startsAt ASC, id ASC. Popular: participantsCount DESC, id ASC. Timestamps содержат offset, PostgreSQL использует TIMESTAMPTZ. |
| Мои события | Объединение созданных событий и событий участия без дублей; обязательное `relation`: `creator`, `participant`, `creator_and_participant`; ongoing относится к upcoming. |
| Компания | Создание только для доступного события; owner сразу член компании и участник события, входит в maxMembers. Лимит 2–100 из исходного API. |
| Владелец | Не может выйти через members/me; передачи владения нет. Для прекращения компании использует удаление. |
| Участие | Не более одной компании одного события для пользователя. Solo → company автоматически и атомарно. Выход и исключение отменяют участие целиком, без перехода обратно в solo. |
| Открытый вход | Join без заявки только при joinType=open, доступном событии, открытом наборе, наличии места и допустимом статусе пользователя. |
| Заявки | JoinType=request; одна pending на пользователя и компанию. После rejected/cancelled разрешена новая запись. `/applications/me`: сначала pending, иначе последняя. Общий `/users/me/applications` возвращает историю всех статусов с пагинацией. |
| Approve | Повторная проверка места, актуальности компании/события и отсутствия другой компании этого события. Заявка, членство и участие изменяются одной транзакцией. |
| Close/open | Close сохраняет компанию и участников, запрещает новые join/application. Open доступен владельцу, если компания не заблокирована и событие актуально. |
| Удаление | Soft delete через deleted_at. Компания исчезает публично, pending-заявки отменяются, участие пользователей этой компании удаляется; история членства может сохраняться. Восстановления нет. |
| Ban | Статус banned и отзыв всех refresh-сессий; защищённые endpoints недоступны, история сохраняется. Unban выполняет admin. |
| Block компании | Компания скрыта от посторонних, но доступна текущим участникам/owner со статусом blocked. Новые действия запрещены, участие сохраняется, pending-заявки получают cancelled/COMPANY_BLOCKED. После completed pending-заявки получают cancelled/EVENT_COMPLETED. |
| Жалобы | На пользователя, событие или компанию с проверкой существования. Повторные жалобы на объект разрешены. Статусы pending/resolved/rejected. |
| Аватар | JPEG/PNG/WEBP, максимум 5 242 880 bytes. Ответ `{ "avatarUrl": "https://..." }`. Ошибки: 413 AVATAR_TOO_LARGE, 415 UNSUPPORTED_AVATAR_TYPE, 500/503 AVATAR_UPLOAD_FAILED. Старый файл сохраняется при любом сбое. |
| Списки | Согласованный перечень растущих списков использует `{ items: [], pagination: { page, limit, total, totalPages } }`. Page=1, limit=20, максимум 100; для пустого результата totalPages=0, выход за последнюю страницу не является ошибкой. Справочники остаются массивами. |
| Ошибки | `{ error: { code, message, details } }`; ошибки полей находятся в `details.fields: Record<string, string[]>`. Подтверждены `PROFILE_INCOMPLETE`, `OWNER_CANNOT_LEAVE`, `ALREADY_IN_EVENT_COMPANY` и коды аватара. |
| Dashboard | `newRegistrations` означает последние 30 календарных дней, включая текущий; предпочтительное имя в контракте — `newRegistrations30d`. |

## Оставшиеся технические решения backend

Контрактные вопросы фронтенда закрыты. До соответствующих этапов backend выбирает
и документирует: способ назначения первого admin, абсолютный срок refresh-сессии
и короткое окно повторной ротации, CSRF-защиту при cross-site cookie, конкретное
хранилище аватаров и механизм фонового завершения событий. Значения URL и OAuth
credentials задаются окружением и не входят в API-контракт.

- [ ] Перед вступлением: пользователь не banned, событие/компания доступны,

- [x] Soft delete: deleted_at, отмена pending заявок, удаление только участия,
      привязанного к удаляемой компании; история может сохраняться. Всё атомарно.
- [x] maxMembers 2–100, уменьшение ниже текущего состава запрещено.
- [ ] Join/create/approve должны использовать общий порядок блокировок и защищать
      и последнее место, и одну компанию на событие. Один count перед insert недостаточен.

Готовность: владелец входит в лимит, не может выйти; solo → company сохраняет
одного участника; leave/kick/delete убирают участие. После soft delete исторические
строки не препятствуют вступлению в другую компанию события. Проверены гонки и откат ошибок.
