# План разработки Poydem API v1

Статус: предложение для обсуждения, реализация бизнес-API ещё не начата.
Основа: предоставленный `poydem-openapi.yaml` (OpenAPI 3.0.3, API 1.0.0),
начальная миграция и текущий код проекта.

## Текущее состояние и объём

Готовы: Gin, `/api/v1`, Request ID, структурированные логи, PostgreSQL,
Docker Compose, миграции, `/health`, `/ready` и базовые тесты.
В `domain`, `usecase` и `repository` пока нет бизнес-реализации.

Контракт содержит 53 операции (сочетания HTTP-метода и пути):

| Блок | Операций |
| --- | ---: |
| Авторизация `/auth/*` | 5 |
| Профиль `/users/me*` | 7 |
| Справочники | 3 |
| События `/events*`, включая создание компании | 8 |
| Компании `/companies*`, включая заявки | 15 |
| Создание жалобы `/reports` | 1 |
| Администрирование `/admin/*` | 14 |

Разрабатываем законченными сценариями: доменные правила → интерфейсы usecase →
реализация репозиториев → HTTP DTO и обработчики → тесты. Каждая новая версия API
имеет свои DTO; доменные сущности не сериализуем напрямую в ответы.

## Решения перед реализацией соответствующих блоков

| Вопрос | Что есть в контракте / БД | Что нужно зафиксировать |
| --- | --- | --- |
| Вход | Google, VK, Telegram; callback с `code`, результат `302` | Первый провайдер, порядок остальных, механизм каждого провайдера, OAuth state, допустимый redirect, обработка отказа и передача результата фронтенду |
| Сессии | Bearer JWT; refresh без тела запроса и без описания cookie | Откуда берётся refresh-токен, срок жизни, ротация, отзыв при logout/ban, текущая сессия или все устройства |
| PATCH | Изменение компании и admin-события использует Input с обязательными полями | Частичный PATCH с отдельными DTO или обязательная передача всех полей; отличие отсутствующего поля от `null` и очистки значения |
| Форматы ответов | Многие response-схемы без `required`; `User.city` не nullable, но `users.city_id` nullable | Какие ключи всегда возвращаем; пустые массивы; представление отсутствующего города; тело ответа загрузки аватара |
| Пагинация | `EventList` содержит метаданные; другие списки — массивы, иногда с page/limit | Сохранить разные форматы или согласовать изменение с фронтендом; пагинация `/users/me/events` сейчас не описана |
| Каталог | Есть `popular`, диапазон дат и `upcoming/past` | Формула популярности, сортировка по умолчанию и стабильный второй ключ, часовой пояс и границы дат, определение завершённого события |
| «Мои» списки | Есть события, компании, заявки | События созданные, посещаемые или оба вида; компании владельца и/или участника; история заявок или только актуальные |
| Участие | PK `(event_id, user_id)` допускает одну запись участия на событие | Выход из компании отменяет участие — подтверждено. Уточнить переход solo → company, поведение при исключении и возможность смены компании |
| Владелец | `owner_id` и отдельные `company_members` | Считать ли владельца участником и учитывать ли в лимите; может ли он выйти; передачи владения в контракте нет |
| Удаление компании | DELETE есть, FK используют NO ACTION | Физическое удаление с обработкой зависимостей или soft delete отдельной миграцией; судьба участников и заявок |
| Модерация | Перечни статусов и действия approve/reject/block/open/close | Разрешённые переходы, поведение повторных действий, видимость скрытых объектов, влияние ban/block на участие и сессии |
| Аватар | Multipart `file`, ответ 200 без схемы | Хранилище, выдача URL, допустимые форматы и размер, удаление старого файла |
| Админ | Есть роль admin, но нет маршрута её выдачи | Как создать первого администратора; период для `newRegistrations`; аудит действий при необходимости |

Предложение для сессий: access JWT и refresh-токен в защищённой HttpOnly cookie;
хранить в БД хеш refresh-токена, срок действия и состояние отзыва. Это проектное
предложение, а не уже согласованная часть контракта. Атрибуты cookie, CORS и защита
от CSRF определяются после уточнения адресов фронтенда и API.

Подтверждённое правило: при выходе пользователя из компании его участие в событии
отменяется. Удаление членства и соответствующего участия выполняется одной
транзакцией, без автоматического перевода в solo. Исключение участника владельцем
и удаление самой компании пока требуют отдельного решения.

Порядок провайдеров предложен с учётом вопроса о сложности: сначала полностью
довести Google, затем подключить Telegram и VK через общий интерфейс. Первый
провайдер включает основную работу с аккаунтами, JWT, refresh и logout; следующие
повторно используют эту часть и добавляют адаптер, настройки и проверки callback.
Рекомендация — сохранить все три в объёме MVP, но подключать последовательно;
наличие зарегистрированных приложений и callback URL влияет на порядок.

По актуальной документации на 19.09.2026:

- [Google](https://developers.google.com/identity/openid-connect/openid-connect)
  поддерживает серверный OpenID Connect flow.
- [Telegram](https://core.telegram.org/bots/telegram-login) поддерживает OIDC
  Authorization Code Flow с PKCE; для настройки нужны бот, Client ID/Secret и
  разрешённые URL. Это подходит под callback с `code` в исходном контракте.
- [VK ID](https://github.com/VKCOM/vkid-web-sdk) использует OAuth flow с настройками
  state и codeVerifier; детали callback и обмена кода нужно согласовать с адаптером.

Оценка относительной сложности: общая авторизация — наиболее крупная задача;
каждый следующий провайдер — отдельная интеграционная подзадача. Точную оценку
в днях стоит давать после выбора сессионной модели и проверки доступов.

## Этап 0. Уточнить и зафиксировать контракт

- [ ] Перенести согласованный OpenAPI в `api/openapi.yaml` под контроль версий.
- [ ] Решить вопросы выше перед началом затрагиваемых ими этапов.
- [ ] Добавить `operationId`, обязательность полей ответов, форматы auth/cookie и ошибок.
- [ ] Уточнить PATCH, загрузку аватара и ошибки 400/401/403/404/409 на нужных операциях.
- [ ] Зафиксировать таблицу прав: гость, пользователь, владелец компании, администратор,
      заблокированный пользователь. Проверки владения выполнять в usecase.
- [ ] Зафиксировать переходы статусов событий, компаний, заявок и жалоб.

Готовность: фронтенд и бэкенд одинаково понимают запросы, ответы, права и спорные
действия. Вопросы поздних этапов не блокируют справочники и общую HTTP-обвязку.

- [ ] Добавить CI: Go-тесты, vet, проверка OpenAPI и миграций на отдельном PostgreSQL.

Готовность: три публичных маршрута работают на реальной БД и возвращают JSON
по контракту; ошибки и пагинация имеют проверенные общие правила.

## Этап 2. Авторизация и основной профиль

Зависимость: этап 1, решения о провайдерах и сессиях.

- [ ] Интерфейс внешнего провайдера и адаптер первого выбранного провайдера.
- [ ] Начало входа, проверка callback и транзакционное создание `users` + `auth_accounts`.
      Повторный/одновременный вход не создаёт дубликаты аккаунта.
- [ ] JWT middleware: проверка токена и статуса пользователя; identity в context.
- [ ] Refresh с ротацией, logout с отзывом, согласованная обработка повторного refresh.
- [ ] GET `/auth/me` и GET `/users/me` используют общий сценарий чтения профиля.
- [ ] PATCH `/users/me`: обновление полей и интересов одной транзакцией.
- [ ] Новая миграция с хранилищем сессий и согласованными ограничениями пользователя.

Готовность: пользователь входит через реального провайдера, обновляет профиль,
обновляет сессию и выходит; неверные, истёкшие и отозванные учётные данные
обрабатываются по контракту. Интеграционные тесты используют адаптер-заглушку
провайдера; реальный callback проверяется отдельно при наличии client credentials.

## Этап 3. События и минимальная модерация

Зависимость: этапы 1–2. Чтение каталога можно готовить после этапа 1 на фикстурах.

- [ ] GET `/events`: поиск, город, категория, диапазон дат, сортировка, пагинация.
- [ ] GET `/events/{eventId}` и публичные участники события.
- [ ] POST `/events` с проверкой справочников, дат и согласованным начальным статусом.
- [ ] Защищённые admin-маршруты списка/деталей/редактирования и approve/reject/block
      событий; создание первого администратора через согласованный служебный механизм.
- [ ] Вычислять `participantsCount` из `event_participants`, `companiesCount` из
      компаний с учётом принятой видимости; избегать N+1 запросов.
- [ ] Применять правила видимости к спискам, деталям, участникам и компаниям события.

Готовность: пользователь создаёт событие, администратор одобряет его, событие
появляется в публичном каталоге. Pending/rejected/blocked не обходят правила
видимости через прямую ссылку.

## Этап 4. Компании и участие

Зависимость: этап 3, решения о владельце, удалении и переходах участия.

- [ ] Список/создание компаний события; детали, PATCH и DELETE компании.
- [ ] Список участников, join открытой компании, выход и исключение участника.
- [ ] При выходе удалить членство и участие в событии одной транзакцией;
      проверить, что пользователь исчез из участников события и его счётчика.
- [ ] Open/close набора с проверкой владения и текущего статуса компании.
- [ ] Создание и отмена solo-участия; переходы между способами участия.
- [ ] GET `/users/me/events` и `/users/me/companies` с согласованной семантикой.
- [ ] Обновлять `company_members` и `event_participants` атомарно; создание компании
      также включает членство/участие владельца, если это правило принято.
- [ ] Проверять `maxMembers` 2–100; запретить уменьшение лимита ниже текущего состава.
- [ ] При конкурирующих join сериализовать проверку свободного места и вставку
      внутри транзакции. Конфликт участия в одном событии переводить в доменную ошибку.

Готовность: параллельные запросы не превышают лимит и не оставляют расхождение
между членством и участием; пользователь не может управлять чужой компанией.

## Этап 5. Заявки в компании

Зависимость: этап 4; approve использует те же правила вступления, что и join.

- [ ] Создание заявки, получение своей заявки, её отмена и список моих заявок.
- [ ] Список заявок компании с фильтром статуса только для уполномоченного пользователя.
- [ ] Одобрение/отклонение; проверка, что `applicationId` принадлежит `companyId` из URL.
- [ ] Одобрение атомарно обновляет заявку, членство и участие в событии.
- [ ] Решить правила повторной подачи после rejected/cancelled и выбора заявки для `/me`.
- [ ] При принятом правиле одной активной заявки добавить частичный UNIQUE для
      `(company_id, user_id) WHERE status = 'pending'`; историю не терять.

Готовность: нет дублирующих активных заявок, двойного одобрения и переполнения при
одновременном approve/join; проигравший запрос получает согласованную ошибку.

- [ ] Admin companies: список и блокировка с согласованными последствиями.
- [ ] Admin reports: список, детали, resolve/reject; заполнение resolved_by/resolved_at.
- [ ] Dashboard: согласованные определения четырёх счётчиков и периода регистраций.
- [ ] Протестировать доступ обычного, заблокированного пользователя и администратора.

Готовность: административные операции доступны только администратору,
повторные действия и недопустимые переходы статусов обрабатываются предсказуемо.

## Этап 7. Аватары и остальные провайдеры

Зависимость: этап 2 и выбранные внешние сервисы; можно делать независимо от этапов 3–6.

- [ ] Интерфейс файлового хранилища и выбранный адаптер.
- [ ] Загрузка/удаление аватара, проверка фактического формата и размера, генерация
      безопасного имени файла; согласованный ответ с URL.
- [ ] Обработка сбоя между записью файла и обновлением профиля; очистка старых файлов.
- [ ] Адаптеры оставшихся провайдеров с проверкой каждого реального callback.
- [ ] Не объединять разные аккаунты по совпадению имени или непроверенных данных;
      связывание аккаунтов требует отдельного продуктового решения.

Готовность: все три заявленных способа входа работают, аватары переживают перезапуск
контейнеров и не оставляют профиль с несуществующим файлом при обработанном сбое.

- [ ] Сверить реализацию всех 53 операций с итоговым OpenAPI, включая ошибки.

- [ ] Проверить права на чужие ресурсы, статусы, пустые выборки, границы пагинации,

- [ ] Проверить миграции на чистой БД и обновление с существующей начальной схемы;

Готовность: весь согласованный контракт реализован; проверки CI и сквозные

## Изменения БД после согласования правил

Начальную `000001` не переписывать: добавлять последующие миграции по мере реализации.

- Таблица сессий/refresh-токенов с хешем токена, expiry и отзывом.
- CHECK для `users.role IN ('user', 'admin')`, `users.status IN ('active', 'banned')`
  и `companies.max_members BETWEEN 2 AND 100` — новые ограничения известны из API.
- NOT NULL и начальные статусы для обязательных по бизнес-правилам полей; перед
  ужесточением проверить и при необходимости заполнить существующие данные.
- Согласованность `participation_type` и `company_id`; принадлежность компании
  указанному событию — кандидат на составной FK после уточнения правил.
- Уникальность активной заявки, если принято соответствующее правило.
- Стратегия удаления компаний и зависимых записей; soft delete только при выборе
  этой модели, с согласованной видимостью в запросах.
- Дополнительные индексы выбирать по реализованным запросам и их планам выполнения.
